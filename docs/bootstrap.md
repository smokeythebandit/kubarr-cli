# Web bootstrap

`kubarr bootstrap` with no arguments starts the browser-based bootstrap wizard. Use `kubarr bootstrap --web` to request the same wizard explicitly. The CLI prints invitation URL(s); on a desktop session it also attempts to open the browser. If that fails, open a printed URL manually. The first step asks **where to install**: select a discovered Kubernetes context, upload a kubeconfig, or install a local single-node k3s cluster. Then configure dashboard access, storage, administrator account, and optional Grafana before reviewing the choices.

```sh
kubarr bootstrap
kubarr bootstrap --web
kubarr bootstrap --web --web-port 8080
```

`--web-port` accepts ports 0–65535; `0` (the default) selects an available port, which is shown in the printed URL. All installation configuration is done in the browser wizard. Selecting an existing context starts read-only cluster checks; the wizard reports their actual progress, then installation progress and a success or failure result. A selected context needs a completed, successful check from the past **five minutes** to begin installation; refresh the checks if they expire. Required failures prevent continuing, while advisory storage and metrics warnings do not. Installation runs its own prerequisite checks again because cluster health can change. For a new local k3s installation, cluster checks are deferred until the cluster is created. Keep the CLI process running until installation finishes. Closing the browser tab does not cancel installation; reopen the printed URL to reconnect. After its one-time invitation has been redeemed, the browser session cookie is checked first, so that same printed URL still works in that browser.

Discovery reads the ordered `KUBECONFIG` file list (first named entry wins), `~/.kube/config`, up to 24 matching `~/.kube/*.yaml`, `*.yml`, or `config-*` files, and `/etc/rancher/k3s/k3s.yaml` if readable. It does not recursively search home or contact a cluster. Discovered context names and source labels are shown; credentials and kubeconfig paths are not returned. Local configurations are trusted operator input: authentication `exec` plugins are not run during discovery but **may run** when checking or installing into that selected local context. An uploaded kubeconfig is never permitted to run authentication plugins. Each check command is time-limited (four seconds), with a 90-second overall check deadline; changing targets replaces the active check and stops its in-group processes. An authentication plugin that detaches into another process group cannot be terminated by that mechanism; its inherited output pipe cannot keep the wizard checks blocked beyond their deadline. Failures display fixed troubleshooting text instead of subprocess output.

The permission checklist samples the installer’s baseline RBAC requirements: each row names its resource and tested scope (typically the `default` namespace used for Helm releases, or cluster scope). A pass is **not** a guarantee of permission in every namespace created or used by the charts, or of a successful install. StorageClass and metrics results are advisory; installation rechecks required cluster prerequisites before changing the cluster.

Selecting **External NFS** in the browser wizard and continuing from Storage runs a separate, required live check from the selected cluster. It creates a temporary namespace, static `Retain` NFS PersistentVolume (forced NFSv4.1), claim, and non-root Pod on **one** Ready Linux node. The Pod runs as UID/GID 1000 (no `fsGroup`), writes and reads a small exclusive file in a new uniquely named `.kubarr-check-*` directory in the specified export, then removes only its own file and directory. The Pod does not receive a Kubernetes service-account token. A check succeeds only after file readback, file/directory removal and confirmed deletion of the temporary Kubernetes resources; it expires after five minutes. Changing the destination, server or export path requires a fresh check. A pass verifies this node and UID/GID only; it does not establish NFS access from every node or the permissions needed by a different application UID/GID (such as 999). Managed NFS requires no external mount check.

The check changes the selected cluster and briefly writes to the external export when you press Continue. Cancelling or replacing it waits for cleanup of the previous run before beginning another; installation cannot start while a storage check is running or cleaning up, even when another storage mode is selected. Object cleanup uses the exact Kubernetes UID returned by creation, with a server-enforced UID precondition on each DELETE. A timed-out creation is only adopted for cleanup if its identity and test configuration can be verified. Abrupt termination, API loss, a stuck NFS unmount, or missing confirmation that the test directory was removed can prevent confirmed cleanup; the check then fails and reports the temporary namespace, PV and possible export test directory for operator inspection. Do not remove unrelated export content. For local single-node k3s, the same external NFS check runs after k3s exists and before application components install.

Uploads are capped at 256 KiB of kubeconfig content. They support embedded bearer tokens or embedded client certificates and keys, and optionally embedded CA data. They must use HTTPS and cannot specify `exec`, `auth-provider`, credential/CA file paths, proxy URL, or insecure TLS. Uploads remain private on the installer host, are kept only for this wizard's lifetime, and are removed on normal shutdown. Abrupt termination (for example SIGKILL or host failure) can leave a private snapshot directory in the host's temporary directory; remove stale `kubarr-target-*` directories locally if necessary. The wizard limits uploaded documents and available targets. Use an SSH tunnel on untrusted networks: the wizard's HTTP transport does not encrypt uploaded credentials.

The selected context is pinned for Kubernetes checks and every installation kubectl/Helm command. Local relative certificate/key references and relative `exec.command` paths are resolved relative to their original kubeconfig; bare executable names continue to use `PATH`. Local single-node installs target a private snapshot of `/etc/rancher/k3s/k3s.yaml`, even when another cluster is reachable. The selected k3s API must be an HTTPS literal loopback address (`127.0.0.1` or `[::1]`) with a port; DNS hostnames, interface addresses, proxy settings, and insecure TLS settings in this k3s config are rejected. An existing invalid k3s file stops installation rather than falling back to another cluster. Fresh installs snapshot the file *after* k3s creates it. k3s is requested to write its original kubeconfig with mode `0600`; permissions of pre-existing original files remain under the host operator's control. The private snapshot remains until the CLI exits so post-install address refresh still uses the installed target.

The browser installation activity reports named stages and safe operation progress: Helm release and workload namespace (distinguished from the Helm release namespace), readiness patches, rollouts, storage configuration, and database initialization. Long-running commands report elapsed wait progress about every ten seconds, followed by success or failure with duration and, when available, numeric exit code. Activity is bounded to the latest 500 entries. It does not include command arguments, chart paths, NFS endpoints, SQL, credentials, or raw subprocess output. If installation fails, subprocess diagnostic output is written locally to the private log whose path the CLI prints. On Unix the file has mode `0600` and is capped at 1 MiB. It may contain secrets from Helm, kubectl, or k3s; inspect it only on the host and remove it when finished. For uploaded kubeconfigs, raw subprocess failure output is **not written** to this log, since tools might echo uploaded credentials. The browser shows a failure result but does not expose subprocess output.

The authenticated `GET /api/status` also includes `access` (null until installation succeeds, otherwise `{kind,url,instructions,pending}`). Its URL comes from validated gateway access information, not installation log text. `GET /api/access` refreshes the installed gateway LoadBalancer Service address on the frozen installation target after success; the bounded, read-only lookup does not test reachability or change any cluster resources. If the address is pending, `url` is null and fixed instructions explain how to check it using the installation's kubeconfig. For port-forward, the loopback URL works only after forwarding is running on the browser's machine (or after an additional SSH tunnel from a remote host). Both endpoints require the wizard session and allowed Host.

The authenticated `GET /api/install-log` downloads `kubarr-install.log` as plain UTF-8 text during or after installation, including on failure. It contains the same curated operation/stage and filtered legacy events as the browser activity feed, plus the safe phase and result; it retains up to 2 MiB independently of the 500-event status window. When earlier complete lines are discarded, the download says so explicitly. This download never reads the private local failure-diagnostics file.

Ctrl-C during installation requests shutdown but does not cancel installation: the HTTP wizard remains available while the install runs, then the CLI exits automatically when it finishes. A second signal is not needed.

## Choose a connection

- **Desktop:** When a display session is detected, the web server binds to loopback (`127.0.0.1`). Use the printed local URL from that machine.
- **Headless, non-SSH:** The server also binds only to loopback. Use a local browser on the machine, or establish an SSH tunnel from your workstation:

  ```sh
  ssh -L 8080:127.0.0.1:8080 <user>@<server>
  ```

   Start `kubarr bootstrap --web --web-port 8080` on the server, then open the complete printed `http://127.0.0.1:8080/#<token>` invitation URL on your workstation. Keep the SSH session/tunnel open.
- **SSH session:** SSH detection takes precedence over desktop detection. The server binds to all IPv4 interfaces. It prints candidate URLs based on the SSH connection's server-side address, addresses reported by `hostname -I`, and loopback. These are candidates, not guarantees; routing and firewall rules may prevent access. Prefer tunneling rather than exposing the wizard remotely:

  ```sh
  ssh -L 8080:127.0.0.1:8080 <user>@<server>
  ```

   Run `kubarr bootstrap --web --web-port 8080` on the server and open the complete printed `http://127.0.0.1:8080/#<token>` invitation URL locally. Replace `<user>@<server>` with your SSH destination. Keep the local forwarding port identical to the wizard port so its Host and Origin checks accept the request.

The wizard uses plain HTTP, not TLS. Anyone able to observe the network traffic can read the administrator password and session. This is especially important for the SSH-mode all-interface listener: use only a trusted network, or use SSH port forwarding as above. Do not treat the invitation link as a substitute for transport encryption.

## Dashboard access

The browser wizard configures the **OpenResty gateway** (`svc/kubarr-gateway` in namespace `openresty`) for all dashboard access modes. Its HTTP service port is **8080**; the backend (`kubarr-backend`, port 8000) stays ClusterIP and is not directly exposed by web installs. The existing form field named `backend_port` represents the **gateway NodePort** when NodePort is selected (default 30080, valid range 30000–32767); it is ignored for LoadBalancer and port-forward.

- **NodePort:** open `http://<node-ip>:30080` (or the chosen gateway NodePort).
- **LoadBalancer:** requires an existing load-balancer controller in the target cluster (for example MetalLB or Cilium on bare metal). The wizard does not install one. Open `http://<assigned-ip-or-hostname>:8080` when an address is assigned. If it is still pending or cannot be read, check `kubectl get svc -n openresty kubarr-gateway --watch` using the selected context; the install does not wait indefinitely for an external address.
- **Port-forward:** run `kubectl port-forward -n openresty svc/kubarr-gateway 8080:8080` using the selected context, then open `http://127.0.0.1:8080` on the forwarding machine. The gateway is ClusterIP in this mode.

For an **existing context**, the backend requires an explicit, successful allocation check before installation. The browser integration must offer an explicit test action: simply loading the page or selecting the access mode must **not** start this check. The authenticated, CSRF-protected `POST /api/loadbalancer-checks` accepts `{"target_id":"…"}`; `GET /api/loadbalancer-checks/{check_id}` reports staged progress and eligibility, and `POST /api/loadbalancer-checks/cancel` accepts `{"check_id":"…"}`. The action creates a randomly named, selectorless TCP Service of type `LoadBalancer` on port 8080 in the actual `openresty` gateway namespace, with no Pods or endpoints. A cloud provider may allocate an external address and **bill for transient resources** when you initiate the test. The check waits up to 45 seconds for an ingress IP or hostname, then deletes only the temporary Service and waits up to two minutes for its absence from the Kubernetes API. Kubernetes deletion honors observed provider finalizers; providers without finalizers may continue releasing external resources afterward. A pass does **not** confirm external cloud-resource deletion or the absence of later charges. Passing results expire after five minutes and apply only to the selected context. This proves recent address allocation, not external reachability, a reserved IP, or that the gateway will receive an address later.

The check resolves the **selected gateway chart** (`KUBARR_CHARTS_DIR/openresty` when overridden, otherwise the official OCI chart), reads its version and renders its namespace and LoadBalancer Service. It uses the rendered labels (including `helm.sh/chart`), Service settings, class and annotations; the probe's unique ownership marker is an **annotation**, not an extra label. For an OCI chart, the later gateway install is pinned to the checked chart version; a changed local chart version fails the start gate. OCI republishing at the same version or editing local chart contents without changing their version can still invalidate this comparison; neither version string is a content digest. If chart metadata cannot be rendered, the check fails rather than assuming labels.

If `openresty` is absent, the check **prepares and retains it** for the future gateway release, with the rendered namespace labels, `app.kubernetes.io/managed-by=Helm`, and Helm ownership annotations `meta.helm.sh/release-name=openresty` and `meta.helm.sh/release-namespace=default`. It remains even if the Service check fails or is cancelled; only the temporary Service is deleted. Existing namespaces are never patched or deleted. An existing namespace without the matching chart labels and Helm ownership fails with an explanation instead of being adopted. There is no namespace emptiness scan or cascading namespace deletion. If a provider cleanup finalizer remains, the wizard never removes it: inspect the reported Service in the selected context and resolve provider cleanup before retrying. A cancelled or replaced check waits for temporary Service deletion before a replacement starts; no installation can begin while it is running, even if another access mode is chosen. No traffic is sent through the probe, and the wizard installs no load-balancer controller.

A new **local k3s** destination cannot select LoadBalancer for installation: there is no existing cluster on which to verify allocation. Select an existing configured context or use NodePort/port-forward. A pending-address timeout on bare metal may mean the cluster lacks an address allocator or usable pool; some implementations also wait for ready endpoints and cannot pass this selectorless, no-traffic test. Investigate the provider outside the wizard, then retry.

The printed invitation contains a bearer token. Redeeming it creates the browser session and consumes the invitation, so the link is single-use. Keep it private; if it is expired, invalid, or already redeemed, restart the CLI to issue a fresh invitation. The browser session remains usable for the running wizard and its progress.

## Verification

To run the browser wizard's Node.js tests (without starting an installer or contacting a cluster):

```sh
node --test code/cli/src/bootstrap_web.test.mjs
```

## CLI builds and releases

The Kubarr repository's normal CI/CD pipeline builds the CLI alongside the application. `.github/workflows/build.yml` builds native Linux x86_64 and ARM64 release binaries, checks that bootstrap supports the web wizard and the legacy install command is absent, and packages each binary with a SHA-256 checksum.

After the normal CI gates pass, `.github/workflows/publish.yml` publishes these artifacts to this repository's GitHub Releases:

- Successful `main` builds update the rolling [`kubarr-cli-latest` release](https://github.com/smokeythebandit/Kubarr/releases/tag/kubarr-cli-latest), used by `https://kubarr.com/install.sh`.
- `v*` tags attach the CLI archives and checksums to the matching versioned release after release E2E and acceptance tests pass.
- Pull requests build the CLI without publishing it.

The assets are `kubarr-linux-x86_64.tar.gz` and `kubarr-linux-aarch64.tar.gz`, each with a matching `.sha256` file. The website hosts the installer script and downloads these Kubarr-owned assets. CLI updates are published by pushing to Kubarr's `main`; a separate website build is only needed when changing the download script itself.
